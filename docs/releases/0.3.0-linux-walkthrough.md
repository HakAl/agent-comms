# Release 0.3.0: walkthrough on a clean Linux machine

This is the release evidence for 0.3.0 and the acceptance walkthrough of
milestone 2 of the [roadmap](../ROADMAP.md): the milestone 1 walkthrough,
repeated on a clean Linux machine. Following only this repository's docs:
install a release, run setup against a project, pick runtimes and create a
small team, get a clean `doctor` report, run the fake-runtime demo, then a
real dispatch, review and approval, with the monitor kept up by the user
service. Every command below was run as the docs give it, in the order
shown, and its exit status and the relevant lines of its output are
recorded. Where the walkthrough had to depart from the doc text, the
departure is marked and listed under
[Departures](#departures-from-the-docs). The record is a frozen snapshot of
one run; it is not parsed by the docs checker and is not kept in step with
later doc changes. It follows the shape of the
[0.2.0 macOS record](0.2.0-macos-walkthrough.md).

The VM clock is UTC; timestamps in the output are the VM's. Each command
ran in a login shell over ssh, one ssh session per block, so no session of
the user remained between blocks; `exit=` is the exit status of the whole
block. The transcripts were scrubbed in the VM before they left it: the home
directory is written `~` and the user's name `<user>`. The signers line
shows the key type without the key, and no key, token, device code or
signature is in this record. The logins ran outside the capture. `[...]`
marks lines left out, here or at the end of a shortened line, and a
one-line command too long for the page is wrapped at its `;`. Every id is
one the walkthrough itself generated.

Two inputs came from the operator and not from the docs' ordinary path, and
both are departures: the Codex login was copied from the operator's own
machine rather than made with `codex login --device-auth` (departure 5), and
the two signing steps were run by the operator from one script holding the
runbook's commands in order (departure 7).

## Departures from the docs

1. **Install at the candidate commit.** `git -C agent-comms checkout
   --detach <commit>` was added to the install block between the clone and
   the build, because the candidate was a branch and not `main`.
2. **Requirements the image lacked.** Git, `xxd`, bubblewrap, nodejs and
   npm were installed with apt, each named by the quickstart's
   requirements; uv was installed per its own docs.
3. **npm prefix.** `npm config set prefix "$HOME/.npm-global"` before
   `npm install -g @openai/codex@0.171.0`, and a line in `~/.profile` that
   puts `~/.npm-global/bin` on `PATH`. The docs leave installing Codex to
   its vendor's instructions; with Debian's npm a global install otherwise
   needs root.
4. **Pinned runtime versions named explicitly.** Both runtimes were
   installed at the pinned version (`@0.171.0`, `bash -s 2.1.330`) and not
   at whatever is newest that day.
5. **Codex login copied.** The operator's Codex login file was copied into
   the VM instead of running `codex login --device-auth` there. Recorded as
   an input; that login path is not evidence from this run.
6. **Architect seat in print mode.** The seat is not interactive over ssh,
   so `agent-comms-seat team-a-architect -- claude -p` was used with the
   operating rules appended and only the mailbox tools allowed.
7. **The signing steps from one script.** The operator ran the runbook's
   approve, gate-merge, merge, verify and push approval commands from a
   script in the VM, in the runbook's order, so that one visit to the
   terminal covered both `APPROVE` prompts. The output of `push_approval
   create` went to a file in the VM because it contains the signature.
8. **`ssh-keygen -q`.** Added to the runbook's key recipe so the
   fingerprint and randomart are not printed into the transcript.

## Findings

1. **A minimal Debian has neither Git nor `xxd`.** Both are named in the
   quickstart's requirements as of this candidate. No change needed.
2. **Python 3.13 works and is not a tested interpreter.** Debian 13 ships
   3.13.5; the wheel built, installed and ran on it, and so did the
   checkout for layer 3. The suite is run on 3.11 and 3.14 only, so this
   run is the only evidence for 3.13.
3. **Without lingering, `service stop` does not outlast the session.** The
   unit stays enabled, so the next login starts the service again. With
   lingering on, `stop` stays stopped. The runbook said only that the
   service stops with the last session; it now says this too.
4. **`service status` in the first seconds of a session exits 3.** Without
   lingering the login has only just started the service, and `status`
   reports that the fresh heartbeat is from the previous process. It is
   accurate and clears with the first pass; waiting a few seconds is
   enough.
5. **The seat warning of the 0.2.0 record did not appear.** Opening the
   seat from the worktree printed no warning with Claude Code 2.1.330.
6. **Workers report sandbox directories.** Asked for the repository's
   top-level directories, each worker also listed names that exist only in
   its sandbox's view of the project. Nothing was written to the worktree.
